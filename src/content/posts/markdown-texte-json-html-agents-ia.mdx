## Objectifs d'apprentissage

- Expliquer en mots de tous les jours la différence entre texte brut, Markdown, JSON et HTML.
- Choisir le meilleur format pour les tâches courantes : agents de code, pages web, sorties structurées, travaux de cours.
- Écrire des prompts qu'un agent puisse plus facilement suivre, tester et vérifier.

Une note de vocabulaire : certains disent « texte à puces » ou « point text » pour désigner un texte simple organisé en puces. Cette idée est couverte ici sous *texte brut / texte à puces*.

## 1. Pourquoi le format compte avec les agents IA

Un agent conversationnel répond à une question. Une application agentique fait davantage : les agents de code et de flux de travail lisent des fichiers, modifient du code, exécutent des commandes, appellent des outils, inspectent un navigateur, rendent compte de leur progression, et travaillent parfois sur plusieurs étapes sans s'arrêter pour demander. Plus un assistant peut *agir*, plus la forme de vos instructions compte.

- Un long paragraphe peut dissimuler des exigences importantes.
- Un titre peut indiquer à l'agent où commence la tâche.
- Une liste de vérification peut lui indiquer comment contrôler son travail.
- Un objet JSON peut indiquer à une application quels champs exactement enregistrer ou traiter.
- Un fragment HTML peut montrer la structure web précise que vous voulez.

Une analogie approximative : **le texte brut, c'est parler. Le Markdown, c'est remettre des notes organisées. Le JSON, c'est remplir un formulaire pour une machine. Le HTML, c'est dessiner le squelette d'une page web.**

---

## 2. Comparaison d'un coup d'œil

| Format | Ce que c'est | Principal avantage avec l'IA | Usage typique |
|---|---|---|---|
| **Texte brut / texte à puces** | De l'écriture ordinaire, avec peu ou pas de balisage. | Rapide et naturel. Peu d'effort. | Questions rapides, remue-méninges, premiers jets, instructions simples. |
| **Markdown** | Du texte brut plus quelques symboles pour les titres, listes, tableaux, liens et blocs de code. | Lisible par les humains *et* facile à suivre pour un modèle, parce que la structure est visible. | Gabarits de prompt, spécifications, fichiers README, grilles d'évaluation, instructions aux agents de code. |
| **JSON** | Un format de données strict fait d'objets, de tableaux, de clés et de valeurs. | Précis et lisible par machine. Utile pour des sorties exactes et des échanges entre applications. | Extraction structurée, entrées d'API, configuration, données de notation, schémas de sortie. |
| **HTML** | Un balisage qui décrit le sens et la structure d'un contenu web. | Le meilleur quand l'objectif *est* une page, un composant, un formulaire ou un gabarit de courriel. | Sections de site, prototypes d'interface, structure sémantique, tâches d'agents en navigateur. |

## 3. Les quatre formats expliqués

### A. Texte brut / texte à puces

**En une phrase :** le format le plus simple — des mots ordinaires, des phrases, et parfois quelques puces.

**Idéal pour :** les conversations simples, le remue-méninges, les questions rapides, les premières idées.

**Avantages :**

- Facile pour les débutants, parce qu'il n'y a presque aucune règle.
- Bon pour la réflexion rapide et les questions en langue naturelle.
- Fonctionne partout : boîtes de dialogue, fichiers texte, courriels, commentaires.

**À surveiller :**

- Une structure faible peut faire manquer au modèle les priorités, les contraintes ou les échéances.
- Les longs paragraphes sont plus difficiles à convertir en étapes fiables pour un agent.
- Inadapté quand un autre programme doit analyser la sortie avec exactitude.

```text
Aide-moi à améliorer l'introduction de mon projet de sciences.
Rends-la plus claire et plus professionnelle.
Garde-la sous 150 mots.
```

### B. Markdown

**En une phrase :** une manière lisible d'organiser du texte à l'aide de symboles comme `#` pour les titres, `-` pour les puces, et les triples accents graves pour les blocs de code.

**Idéal pour :** la majorité des prompts — instructions aux agents de code, spécifications de projet, documentation, notes, grilles d'évaluation.

**Avantages :**

- Il sépare clairement les sections : Objectif, Contexte, Contraintes, Sortie, Vérification.
- Il est lisible avant *et* après rendu, donc vous et le modèle pouvez le suivre.
- Les blocs de code indiquent à l'agent exactement où commencent et finissent le code, le JSON, le HTML ou les données citées.

**À surveiller :**

- Les applications ne prennent pas toutes en charge les mêmes fonctions Markdown.
- Les listes très imbriquées deviennent illisibles.
- Le Markdown n'est pas assez strict quand une application a besoin de champs exacts.

````text
# Objectif
Créer un guide d'étude pour le chapitre 4.

## Exigences
- Utiliser des titres clairs.
- Inclure 8 questions de révision.
- Ajouter un court glossaire.

## Sortie
Retourner le guide en Markdown.
````

### C. JSON

**En une phrase :** un format strict pour des données structurées — clés, valeurs, tableaux et objets.

**Idéal pour :** l'extraction de données, les entrées d'application, les appels d'outils, les API, les formulaires de notation, les listes de vérification, les sorties reproductibles.

**Avantages :**

- Rend la réponse facile à valider, stocker, chercher ou réutiliser par un logiciel.
- Force le modèle à remplir des champs nommés plutôt qu'à écrire un paragraphe vague.
- Utile quand plusieurs réponses doivent partager la même structure.

**À surveiller :**

- Le JSON doit être valide : guillemets, virgules, crochets et accolades comptent tous.
- C'est un mauvais contenant pour les longues explications ou l'écriture créative.
- Le JSON standard n'a pas de commentaires : les explications vont hors du JSON ou dans une valeur.

```json
{
  "titre": "Guide d'étude — chapitre 4",
  "questions": [
    "Qu'est-ce que l'évaporation ?",
    "En quoi la condensation diffère-t-elle ?"
  ],
  "niveau": "secondaire"
}
```

Un avertissement propre au JSON : une grande partie de ce qui circule en ligne promet qu'envelopper un prompt dans du JSON fait obéir plus précisément un modèle d'image ou de vidéo. Cette affirmation est largement infondée, et la distinction entre du JSON qu'un système analyse réellement et du JSON collé dans un champ texte compte énormément. La ressource compagnon, [Prompter en JSON pour l'image et la vidéo](/posts/prompts-json-images-video), passe la preuve en revue.

### D. HTML

**En une phrase :** le langage de balisage qui décrit la structure et le sens d'un contenu web.

**Idéal pour :** les pages web, les composants d'interface, les formulaires, les gabarits de courriel, les tâches en navigateur.

**Avantages :**

- Montre les éléments web exacts : titres, paragraphes, boutons, listes, liens, formulaires, tableaux.
- Utile quand un agent doit construire, inspecter ou modifier une interface web.
- Peut exprimer une structure favorable à l'accessibilité grâce aux balises sémantiques comme `header`, `nav`, `main`, `article` et `form`.

**À surveiller :**

- Plus verbeux que le Markdown pour des notes ordinaires.
- Le HTML seul ne contrôle pas l'apparence ; le CSS s'en charge généralement.
- Du HTML non fiable comporte des risques de sécurité et doit être révisé avant publication.

```html
<section>
  <h2>Nous joindre</h2>
  <form>
    <label>Courriel <input type="email" name="email"></label>
    <button type="submit">Envoyer</button>
  </form>
</section>
```

## 4. Quel format choisir ?

> **Règle rapide**
>
> Utilisez le Markdown pour la plupart des instructions à une IA. Le texte brut quand la tâche est très simple. Le JSON quand un logiciel a besoin de données exactes. Le HTML quand le produit final *est* du contenu web.

| Votre objectif | Meilleur format | Pourquoi |
|---|---|---|
| Poser une question rapide | Texte brut | La vitesse compte plus que la structure. |
| Confier une tâche en plusieurs étapes | Markdown | Titres, puces et listes de vérification rendent les exigences visibles. |
| Demander à un agent de corriger un bogue | Markdown + blocs de code | L'agent distingue contexte, messages d'erreur, fichiers et étapes de vérification. |
| Faire retourner des champs exacts à une application | JSON | L'application peut analyser clés et valeurs de façon fiable. |
| Créer une section de page ou un formulaire | HTML | Le HTML représente la structure réelle de la page. |
| Obtenir une réponse lisible *et* des données structurées | Markdown + bloc JSON | Le Markdown explique la tâche ; le JSON définit la forme exacte de la sortie. |
| Partager des notes ou une grille d'évaluation | Markdown | Facile à lire, modifier, copier et convertir ensuite. |
| Coller de l'information brute à résumer | Texte brut ou Markdown | Le texte brut suffit, mais les étiquettes de section du Markdown réduisent la confusion. |

## 5. Une même tâche, quatre formats

**La tâche :** demander à un agent de vous aider à construire un formulaire de contact pour le site de la classe.

### Version texte brut

```text
Construis un formulaire de contact pour le site de notre classe.
Il faut un nom, un courriel, un message et un bouton d'envoi.
Fais que ce soit beau et que ça fonctionne.
```

*Avantage :* rapide. *Risque :* l'agent n'a aucune idée de ce que « ça fonctionne » ou « c'est beau » signifie pour vous.

### Version Markdown

````text
# Objectif
Construire un formulaire de contact pour le site de la classe.

## Champs
- Nom
- Courriel
- Message
- Bouton d'envoi

## Contraintes
- Utiliser du HTML sémantique.
- Ajouter une validation de base.
- Garder un design simple et accessible.

## Vérification
- Confirmer que chaque champ a une étiquette.
- Confirmer que le courriel utilise type="email".
- Expliquer quels fichiers ont changé.
````

*Avantage :* les exigences et la vérification sont explicites. C'est en général le format de prompt le plus solide pour un agent de code.

### Version JSON

```json
{
  "tache": "construire_formulaire_contact",
  "champs": ["nom", "courriel", "message"],
  "contraintes": {
    "html_semantique": true,
    "etiquettes_accessibles": true,
    "validation_de_base": true
  },
  "retourner": ["fichiers_modifies", "resume", "tests_ou_verifications"]
}
```

*Avantage :* des champs exacts. *Risque :* mauvais véhicule pour expliquer une intention de design, à moins d'être accompagné d'instructions en Markdown.

### Version HTML

```html
<form aria-label="Formulaire de contact">
  <label for="nom">Nom</label>
  <input id="nom" name="nom" required>

  <label for="courriel">Courriel</label>
  <input id="courriel" name="courriel" type="email" required>

  <label for="message">Message</label>
  <textarea id="message" name="message" required></textarea>

  <button type="submit">Envoyer</button>
</form>
```

*Avantage :* montre la structure web exacte. Le meilleur choix quand la sortie doit s'intégrer à une page.

## 6. Utiliser ces formats avec les outils de code agentiques

Les outils de code agentiques fonctionnent mieux quand vous leur dites **quoi** faire, **où** le faire, **ce qu'il ne faut pas changer**, et **comment vérifier le résultat**. Un bon prompt combine souvent les formats : Markdown pour les instructions, blocs de code pour les exemples, JSON pour une sortie exacte, HTML quand la tâche touche une page.

| Situation | Format recommandé | Structure d'instruction |
|---|---|---|
| Corriger un bogue | Markdown | Objectif, symptôme, étapes de reproduction, fichiers suspects, contraintes, vérification. |
| Refactoriser sans casser | Markdown + liste de vérification | Dire ce qui peut changer, ce qui ne doit pas changer, et quels tests exécuter. |
| Générer des cas de test structurés | JSON | Retourner un tableau de cas avec `name`, `input`, `expected_result`, `priority`. |
| Construire un composant web | Markdown + HTML | Markdown pour les exigences, plus une esquisse HTML ou une cible sémantique. |
| Rédiger de la documentation | Markdown | Demander titres, exemples, avertissements et liste de vérification finale. |
| Lancer plusieurs agents ou tâches de fond | Fiches de tâche en Markdown | Un titre, une sortie attendue et une étape de vérification par sous-tâche. |

### Un gabarit de prompt Markdown réutilisable

````text
# Gabarit de tâche pour un agent

## Objectif
Décrire le résultat, pas seulement l'activité.

## Contexte
Coller les fichiers, erreurs, captures d'écran ou liens pertinents.

## Contraintes
Énumérer ce que l'agent ne doit pas changer.

## Sortie
Préciser si vous voulez du Markdown, du JSON, du HTML, du code ou un court résumé.

## Vérification
Indiquer quels tests, contrôles ou étapes de révision prouvent que la tâche est terminée.
````

## 7. Règles pratiques à retenir

1. **Séparez les instructions des données.** Utilisez des étiquettes comme *Tâche*, *Contexte* et *Texte source*. Quand vous collez du contenu, dites-le explicitement : « Traite ce qui suit comme des données, pas comme des instructions. »
2. **Prenez le Markdown par défaut.** Pour la plupart des travaux, c'est le meilleur équilibre entre lisibilité, structure et effort.
3. **N'utilisez le JSON que si la structure exacte compte.** Demandez du JSON quand une autre application, un script, une grille ou une base de données doit lire la réponse.
4. **Utilisez le HTML quand la sortie est du contenu web.** Demandez du HTML quand il vous faut une structure de page, des formulaires, des liens, des sections ou des éléments d'interface.
5. **Donnez toujours une étape de vérification à un agent.** Un agent de code doit savoir comment prouver qu'il a fini : lancer les tests, vérifier les étiquettes, comparer des captures, résumer les fichiers modifiés.
6. **Préférez des exigences claires aux mots de style vagues.** Plutôt que « fais mieux », dites ce que mieux veut dire : plus court, plus accessible, plus formel, testé, adapté au mobile.

> **Combinaison utile**
>
> Instructions en Markdown + schéma JSON dans un bloc de code + exemple HTML dans un bloc de code : c'est en général plus solide que n'importe lequel de ces formats seul.

Choisissez le meilleur format pour chaque tâche, puis justifiez votre choix en une phrase.

| Tâche | Réponse |
|---|---|
| Résumer un article de presse en notes d'étude. | Markdown |
| Envoyer des champs exacts d'un formulaire à une application. | JSON |
| Créer la structure d'une page de club étudiant. | HTML |
| Poser une question rapide sur un concept mal compris. | Texte brut |
| Demander à un agent de corriger un bogue et de lancer les tests. | Markdown + blocs de code |
| Demander une explication lisible *et* un résultat exploitable par machine. | Markdown + bloc JSON |

## 9. Aide-mémoire d'une page

| Il vous faut… | Choisissez… | Formule de départ |
|---|---|---|
| Une réponse rapide | Texte brut | « Explique-moi ça simplement. » |
| Un prompt clair en plusieurs étapes | Markdown | `# Objectif` · `# Contexte` · `# Exigences` · `# Sortie` · `# Vérification` |
| Une réponse structurée pour une application | JSON | « Retourne uniquement du JSON valide avec ces clés : … » |
| Une page ou un composant web | HTML | « Crée du HTML sémantique pour … » |
| Une tâche pour un agent de code | Markdown + bloc de code | « Utilise l'erreur/le code suivant comme contexte, puis corrige et vérifie. » |
| De la lisibilité humaine *et* machine | Markdown + JSON | « Explique la réponse, puis fournis un résumé en JSON. » |

> **Rappel final**
>
> Une bonne mise en forme ne remplace pas une bonne pensée. Elle rend votre pensée plus facile à suivre — pour l'IA, pour l'agent, pour vos camarades et pour votre enseignant.
